# Contributing to Raven

## Pull requests

- Base your branch on the latest `main` and keep it focused on one feature or fix.
- CI (`Build` and `Browser backend`) must pass before a pull request is merged.
- Files under `bindings/` are generated by `tools/bindgen`: regenerate them instead of editing or merging them by hand.

## Merging

`main` is protected by a merge queue: click **Merge when ready** and GitHub runs CI on the
pull request as it will land on `main`, with the pull requests queued before it, before
merging it. Never bypass the queue.

Several pull requests that touch the same files (`CMakeLists.txt`, `tests/CMakeLists.txt`,
`include/raven/raven_style.h`, `src/widget/style.c`, the platform backends...) are the riskiest
case: each one passes CI on its own, but they can break once combined. Merge them one at a
time and wait for CI on `main` to be green before the next one.

## Resolving conflicts

When a branch conflicts with `main`, keep **both sides' additions**. Never resolve a conflict
by taking one side's whole file ("accept ours/theirs" on the file): the other side's changes
are silently lost and nothing tells you until CI fails on `main`. Lists that both sides grow
(enums, color tables, CMake source lists, the XML schema, docs tables) need both entries, and
counts that depend on them (for example the number of theme colors) need updating.

After resolving, build and run the tests locally, then check that no file lost a side:

```sh
python tools/check_merges.py HEAD~1..HEAD   # the merge you just made
python tools/check_merges.py --pr 123       # the merge of pull request #123
```

The script lists every file whose merged version is exactly one side's while the other side
had changed it too.
