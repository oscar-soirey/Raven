Moving from Qt to Raven

A guide for teams that build desktop tools with Qt Widgets or Qt Quick and want to move them, in whole or in part, to Raven.

Applies to C, C++, Rust, Python, Go, C#, Zig and LuaJIT · examples in C and C++

1. In one page

Raven is a GUI library written in C11, with no dependency, made for editors and tools. Where Qt is a framework that brings its own object model, its own containers, its own build step and its own runtime, Raven is a single library behind a single header, Raven.h, that your program calls.

  • Every widget, window, texture, font or timer is an opaque handle, a Rid. There is no class hierarchy to derive from and no meta-object compiler.
  • Interfaces are written in XML (the equivalent of a .ui file or of QML) or built with the C API, or both. The code, in C, C++ or any language with a binding, loads the XML, binds the actions it names and finds its widgets by name.
  • Signals and slots become callbacks (one function per event of a widget) and named actions (OnClicked="file.save", bound once with Raction_bind).
  • The loop belongs to you: while (Rwait_frame(-1.0)) {} replaces QApplication::exec().
  • Rendering is Vulkan, on its own render thread. Glass materials, springs, docking, a code editor, a node graph, a timeline and effects written as shaders are part of the library.

The typical port keeps the logic of the application (its model, its file formats, its algorithms) and rewrites the layer that creates widgets and reacts to them. Because Raven has bindings for C++, the C++ code of a Qt application can usually stay C++.

4. The application and its loop

A Qt program hands control to exec(). A Raven program keeps it: each call to Rwait_frame waits for something to happen (input, a timer, an animation, a task), handles it and draws the windows that changed. It returns 0 once Rquit was called or the last window was closed.

Qt

#include <QApplication>
#include <QPushButton>

int main(int argc, char** argv) {
    QApplication app(argc, argv);
    QPushButton button("Quit");
    QObject::connect(&button, &QPushButton::clicked, &app, &QApplication::quit);
    button.show();
    return app.exec();
}

Raven

#include <Raven.h>

static void on_quit(Rid button, void* user_data) { Rquit(0); }

int main(void) {
    if (!Rinit(R_BACKEND_VULKAN)) return 1;
    Rid window = Rwindow_create("Hello", 320, 160, R_WINDOW_DEFAULT);
    Rid button = Rbutton_create("Quit");
    Rbutton_set_clicked_callback(button, on_quit, NULL);
    Rwindow_set_content(window, button);
    while (Rwait_frame(-1.0)) {}
    Rshutdown();
    return Rget_exit_code();
}

Because the loop is yours, a tool that also runs a simulation or a game can call Rdraw_frame() once per iteration of its own loop instead of waiting. Rset_frame_callback runs a function every frame when that is more convenient.

5. Objects, ownership and errors

  • Handles. Every object is a Rid, a 32-bit handle with a type and a generation. Using a destroyed or wrong handle does not crash: the call reports R_ERROR_INVALID_ID through the error callback (Rerror_set_callback) and returns a neutral value. This replaces the QPointer idiom.
  • Ownership. As with QObject parents, a widget added to a parent (Rwidget_add_child, Rwindow_set_content) is owned by it and destroyed with it. A widget that is never added must be destroyed with Rwidget_destroy.
  • Finding widgets. Rwidget_find(window_or_widget, "name") replaces findChild; the name is the Name attribute of the XML or Rwidget_set_name.
  • Data on widgets. Rwidget_set_user_handle stores a pointer on a widget, as setProperty or a subclass member would.
  • Threads. Like Qt widgets, Raven is called from the thread that called Rinit. See Timers and threads.

7. Signals and slots

Raven has two mechanisms, and most Qt connections map to one of them.

Callbacks: one function per event of a widget

// Qt
connect(slider, &QSlider::valueChanged, this, &Panel::onVolume);

// Raven
static void on_volume(Rid slider, float value, void* user_data) {
    Panel* panel = (Panel*)user_data;
    panel_set_volume(panel, value);
}
Rslider_set_changed_callback(slider, on_volume, panel);

A widget has one callback per event. Where Qt connects several slots to one signal, call them from the callback, or use an action.

Actions: named commands, as QAction

A button, a menu item, a shortcut or a link fire an action by its name. The application binds each name once, wherever the action is fired from:

<MenuItem Text="Save" Shortcut="Ctrl+S" OnClicked="file.save"/>
<Button Text="Save" OnClicked="file.save"/>
static void on_save(Rid sender, const char* action, void* user_data) { document_save(); }
Raction_bind("file.save", on_save, NULL);

Raction_fire("file.save", R_INVALID_ID) triggers it from code, as QAction::trigger. Raction_set_default_handler catches actions nobody bound, which is useful while porting.

Custom signals

For signals of your own model classes, keep the observer mechanism you already have (or a plain list of function pointers). Raven only deals with the user interface.

8. .ui files and QML: XML

A Raven interface is an XML document. It is loaded from a file at run time, with live reload while you design (Rwindow_create_from_xml_file), or from text compiled into the program (Rwindow_create_from_xml). The Raven IDE (raven_designer) edits it visually, as Qt Designer edits a .ui file.

From QML

QML's declarative tree, bindings and states have these counterparts:

  • Components (Card.qml) become declared tags with parameters: <Widget Name="Card" Title="Untitled"><Label Text="{Title}"/></Widget>, used as <Card Title="Inbox"/>.
  • Repeater becomes <Repeat Count="3" Var="i"> or <ForEach Items="A|B|C" Var="item">; Loader becomes <Include Source="part.xml"/>; conditions become <If Test="...">.
  • Property bindings are not reactive: the code sets values when they change (Rlabel_set_text...). Most QML bindings in tools are a handful of labels and enabled states, which become a few lines in the callbacks.
  • Animations: Raven animates by itself (springs for movements, transitions on appearance); custom ones use Rdraw_spring in a paint callback.

The interface in XML, the code in C++

The XML names the actions and the widgets; the code binds the actions and finds the widgets by name. It is the closest thing to a QML file with its JavaScript, with the code in your own language, and the window follows the XML when it is saved while the program runs:

<!-- main.xml -->
<Window Title="Hello" Width="400" Height="200">
    <VBox Spacing="12" Slot.Padding="24">
        <Label Name="status" Text="Not clicked yet"/>
        <Button Text="Click me" Style="Primary" OnClicked="hello.clicked"/>
    </VBox>
</Window>
// main.cpp
#include <Raven.h>
#include <string>

static Rid window;
static int clicks = 0;

int main() {
    if (!Rinit(R_BACKEND_VULKAN)) return 1;
    Raction_bind("hello.clicked", [](Rid, const char*, void*) {
        clicks++;
        Rlabel_set_text(Rwidget_find(window, "status"), (std::to_string(clicks) + " clicks").c_str());
    }, nullptr);
    window = Rwindow_create_from_xml_file("main.xml");
    while (Rdraw_frame()) {}
    Rshutdown();
}
# CMakeLists.txt
find_package(raven REQUIRED)
add_executable(hello main.cpp)
target_link_libraries(hello PRIVATE raven::raven)

9. Style sheets and palettes: themes

Qt combines a platform style, a palette and style sheets. Raven has one theme in use at a time, with colors (RColorRole), metrics (RMetric), a font and a material.

  • Built-in themes: Rtheme_apply(R_THEME_DARK), R_THEME_LIGHT, R_THEME_GLASS_DARK, R_THEME_GLASS_LIGHT, and the two high-contrast themes.
  • Theme files replace QSS: Rtheme_load("studio.theme") then Rtheme_use("Studio"). They are reloaded when saved.
  • Styles for a widget type or a class replace selectors: Rtheme_set_style_color("Button", "danger", R_COLOR_ACCENT, ...) and Class="danger" on the widget, as QPushButton[class="danger"] in QSS.
  • A part of a window can carry its own theme (a dark sidebar in a light window).
  • Per-widget overrides: Background, Color.Text, Metric.ControlHeight... in XML.
  • Materials have no Qt equivalent: frosted, clear or tinted glass, blurred panels, windows that show the desktop behind them.

QSS properties map to theme values: background-color to Color.Panel or Background, color to Color.Text, border-radius to CornerRadius or Metric.CornerRadius, padding to Padding or Metric.PaddingX, and :hover / :pressed states to Color.ControlHovered and Color.ControlPressed.

10. QPainter: custom widgets, drawing and effects

Where Qt subclasses QWidget and overrides paintEvent, mousePressEvent and sizeHint, Raven creates a custom widget and gives it callbacks:

static void paint(Rid widget, RPainter* painter, float width, float height, void* user_data) {
    Rdraw_rect(painter, 0, 0, width, height, 12.0f, 0.10f, 0.10f, 0.12f, 1.0f);
    Rdraw_text(painter, R_INVALID_ID, 16.0f, 16.0f, 14.0f, "Level meter", 1, 1, 1, 1);

Rid meter = Rwidget_create(R_WIDGET_CUSTOM);
Rcustom_set_paint_callback(meter, paint, NULL);

Coordinates are logical units from the top left of the widget; the painter handles high-DPI scaling, clipping and opacity.

Effects (shaders)

Where a Qt application would reach for QOpenGLWidget or ShaderEffect in QML just to draw an animated background or a glow, Raven runs fragment shaders on any rounded rectangle: built-in effects (<Border Effect="aurora">, neon, shimmer, ripple...) or your own, written in GLSL with raven_effect.glsl and drawn with Rdraw_shader. See Writing effects (shaders).

Tearing works as in Qt Creator or Visual Studio: a tab dragged out of the area takes its panel to a window of its own; dragging the tab of that window over an area of the same family shows where it will dock; a double click on that tab, or closing the window, puts the panel back where it was. Functions that take a panel keep working on panels that are floating.

12. Dialogs, files and the clipboard

  • Modal dialogs. QDialog::exec() becomes Rdialog_run(window, content), which returns the code passed to Rdialog_close. The content is any widget, usually created from XML. The content is destroyed when the dialog closes: read its fields in the callback of the button that closes it.
  • Non-blocking dialogs. QDialog::open() becomes Rdialog_open(window, content, closed, user_data).
  • Message boxes. QMessageBox::question becomes Rmessage_box(window, "Title", "Text", R_MESSAGE_YES_NO_CANCEL), which returns R_MESSAGE_RESULT_YES, _NO or _CANCEL.
  • File dialogs. QFileDialog::getOpenFileName becomes Rfile_dialog_open(&desc) with an RFileDialogDesc (title, filters, default name); the native dialog of the system is used.
  • Files. Rfile_read and Rfile_write read and write whole files with UTF-8 paths; anything more elaborate stays with your own file code.
  • Clipboard. Rclipboard_set_text and Rclipboard_get_text.
  • Drag and drop from other applications: Rwindow_set_drop_callback.

13. Model/view: lists, trees and editors

Raven does not have a model abstraction such as QAbstractItemModel. Views are filled directly, or asked for their rows on demand:

  • A list of any length: Rlist_view_set_virtual_items(list, count, item_text, model). The callback returns the text of a row when it is drawn, which replaces data(index, Qt::DisplayRole). When the model changes, call it again with the new count.
  • A tree: Rtree_view_add_item(tree, parent_item, text), with Rtree_item_set_user_handle to keep a pointer to your node, as Qt::UserRole.
  • Icons in a grid with names, for thousands of files: TileView, virtualized.
  • Property editors, as in the Raven IDE: build rows of labels and inputs in a VBox, grouped with Expander.
  • Code: TextEditor has languages (colors, completion through Rtext_editor_set_completion_callback, brackets, indentation), markers for errors and warnings, and Markdown.

15. Translations

Qt extracts strings with lupdate, translates them in Linguist and loads .qm files. Raven keeps translations in CSV tables, one column per language, which any spreadsheet or the Translations panel of the Raven IDE edits:

key,en,fr,ar
file.open,Open,Ouvrir,فتح
items.one,{n} item,{n} élément,{n} عنصر
items.other,{n} items,{n} éléments,{n} عناصر
Rlocale_load_csv("strings.csv");
Rlocale_set_language(Rlocale_get_system_language());
Rlabel_set_text(label, Rtr("file.open"));          // tr("Open")
Rlabel_set_text(count, Rtr_plural("items", n));    // tr("%n item(s)", "", n)

In XML, Text="@file.open". Plural rules, numbers in the conventions of each language, right-to-left layouts, bidirectional text, Arabic shaping and emoji are handled by Raven. Porting: export the source and translated texts of your .ts files into the CSV columns, and replace tr("...") with keys.

16. OpenGL and Vulkan content

A Viewport shows what the application renders, in one of three ways:

  1. A texture. The application renders into a Vulkan image (zero copy, Rvulkan_texture_create_from_image_view), shared memory for OpenGL, or CPU pixels, and gives it with Rviewport_set_texture. The closest to QOpenGLWidget rendering into a framebuffer object.
  2. A draw callback inside the render pass of Raven: Rviewport_set_draw_callback, called on the render thread with the command buffer.
  3. A native child window for any API: Rviewport_set_native, as QWindow::createWindowContainer.

With Vulkan, Raven can also use the instance and device of the application (raven_vulkan.h), so that a 3D engine and its editor share one device.

17. Accessibility

As Qt does through QAccessible, Raven speaks to the screen readers of each system: Narrator and NVDA through UI Automation on Windows, VoiceOver on macOS, Orca through AT-SPI on Linux. Standard widgets need nothing. Give accessible names to custom widgets and to buttons without text (raven_accessibility.h). The user can scale the text, use high-contrast themes, color filters and reduced motion.

18. Building and shipping

CMake

# Qt
find_package(Qt6 REQUIRED COMPONENTS Widgets)
set(CMAKE_AUTOMOC ON)
set(CMAKE_AUTOUIC ON)
add_executable(tool main.cpp mainwindow.cpp mainwindow.ui)
target_link_libraries(tool PRIVATE Qt6::Widgets)

# Raven
find_package(raven REQUIRED)
add_executable(tool main.cpp)
target_link_libraries(tool PRIVATE raven::raven)

Point CMake at the Raven package with CMAKE_PREFIX_PATH (the folder with bin/, include/ and lib/). There is no moc, uic or rcc step: the XML is read when the program runs.

Shipping

  • Static linking puts everything in the executable; there are no plug-ins to deploy (no platforms/qwindows.dll, no windeployqt).
  • The machine needs a Vulkan driver, which current graphics drivers include on Windows and Linux; on macOS, MoltenVK.
  • Interfaces loaded from .xml files are shipped next to the program, with their images and fonts; an interface compiled into the program as text needs no file at run time.

20. What Raven leaves to other libraries

Raven is a user-interface library. These Qt modules have no counterpart in it; keep a library you trust for each:

  • Networking (Qt Network): libcurl, your platform's HTTP client, or the standard library of your language.
  • Databases (Qt SQL): SQLite and the drivers of your database.
  • Multimedia (Qt Multimedia): miniaudio, FFmpeg, GStreamer.
  • Printing (Qt Print Support): generate a PDF (for example with a PDF library) and open it with the system.
  • Settings (QSettings): a small INI or JSON file in the configuration folder of the user.
  • Containers and strings (QString, QList, QHash): the standard library of your language. Raven's texts are UTF-8 const char*.

21. A migration plan

  1. Separate the logic from the interface. Move what does not depend on Qt Widgets (model, file formats, algorithms) behind plain functions or classes. Replace QString and Qt containers there with standard types; this step is useful even before Raven.
  2. Inventory the interface. List windows, dialogs, custom widgets, style sheets, docks, threads and translations. Use the tables of this guide to give each one its Raven counterpart, and mark what needs a library from section 20.
  3. Start with one window. Write it in XML in the Raven IDE and bind its actions to the existing logic. Keep the Qt application running beside it during the transition.
  4. Port the custom widgets. Each paintEvent becomes a paint callback; each event handler becomes a case of the event callback.
  5. Port the styling. Choose a built-in theme close to your look, then write a theme file with your colors and the styles of your classes.
  6. Port translations. Convert the .ts files to CSV columns and replace tr() with keys.
  7. Move threads. Replace QThread workers with Rtask_run_async, and queued connections with Rtask_post.
  8. Remove Qt. When the last window is ported, drop the Qt dependency, the moc step and the deployment scripts.

22. Checklist

  • Every connect has a callback or an action.
  • Every findChild uses a Name and Rwidget_find.
  • Every widget created and not added to a parent is destroyed.
  • Only the UI thread calls Raven, except the thread-safe functions.
  • Dialog fields are read before the dialog closes.
  • Dock layouts are saved with Rdock_area_save_layout where saveState was used.
  • Every tr() became a key in a CSV table.
  • Style sheets became a theme file and classes.
  • The build uses find_package(raven) and target_link_libraries(... raven::raven).
  • The program was tested with a screen reader and in a right-to-left language.
