raven_core.h

Lightweight, multithreaded, retained-mode GUI library in C.

raven_core.h : base types, lifecycle, main loop, threading, errors.

Conventions: - every object is an opaque Rid handle, R_INVALID_ID on failure - functions are R<object>_<action>: Rwindow_create, Rwindow_destroy,

    Rwindow_is_valid, Rwindow_set_title, Rwindow_get_size...

- types are RName (RInitDesc, REvent, RKey), callbacks are RNameCallback,

    constants and enum values are R_NAME

- booleans are ints (R_TRUE / R_FALSE), colors are float r, g, b, a - strings are UTF-8 and always copied by the library

Threading: unless a function is documented as thread-safe, it must be called from the UI thread (the thread that called Rinit).

Memory

void Rset_allocator(const RAllocator* allocator);

Replaces the allocator of Raven with the functions of the application (an engine allocator, a tracker...). NULL selects the allocator of Raven again. Must be called before Rinit, and before any other function that allocates. The functions are called from several threads; alloc must return memory aligned for any type (16 bytes).

const RAllocator* Rallocator_get_system(void);
returns
An allocator that forwards to malloc, realloc and free of the C runtime: Rset_allocator(Rallocator_get_system()) is how memory tools that follow malloc (Valgrind, heap profilers) see the blocks of Raven. The environment variable RAVEN_ALLOCATOR=system does the same without recompiling, and it is the default in a build with AddressSanitizer.
void* Rmemory_alloc(size_t size);

Memory from the allocator of Raven (or from the one given to Rset_allocator), for the application: custom widgets, pixel buffers. Aligned on 16 bytes. Never returns NULL: running out of memory is a fatal error. Thread-safe.

Resizes a block, keeping its content. A NULL block is allocated. Thread-safe.

Main Loop

int Rdraw_frame(void);

Produces one frame: processes the pending OS events without waiting, runs the posted tasks and the timers, then lays out, paints and submits every window that changed. A window in which nothing changed is not drawn again, so the call is cheap when the UI is idle.

returns
R_FALSE once Rquit was called or the last window is closed.
int Rwait_frame(double timeout_seconds);

Same as Rdraw_frame, but first sleeps until there is something to do: an OS event, a posted task, a timer, an animation, a pending redraw.

timeout_seconds
Longest sleep. Negative sleeps without limit, 0 does not sleep.
void Rquit(int exit_code);

Makes Rdraw_frame and Rwait_frame return R_FALSE. Thread-safe.

int Rget_exit_code(void);
returns
The code given to Rquit, 0 when the last window was closed.
int Ris_running(void);
returns
R_FALSE once Rquit was called or every window is closed.
void Rpoll_events(void);

Processes the pending OS events without producing a frame. Rdraw_frame does it already: only useful to keep the windows responsive during a long operation.

void Rwait_events(double timeout_seconds);

timeout_seconds

Actions

Actions connect widgets to application code by name. A widget carries an action name (set from XML with OnClicked="file.save", or from C with Rwidget_set_action); when its main event fires, the function bound to that name is called. typedef void (*RDeviceResetCallback)(void* user_data);
void Rset_device_reset_callback(RDeviceResetCallback callback, void* user_data);

Registers a function called after Raven recovered from the loss of the GPU device (a driver reset or update, a GPU removed, a long sleep). Raven starts the backend again and remakes by itself the surfaces of the windows, the fonts, the shaders, the textures made from image files and the small textures (up to 256 x 256). The larger textures made from pixels keep their handle and size but are transparent until Rtexture_update fills them again, which is what this function is for. Textures that wrap objects of the backend must be made again, and the Vulkan handles have changed. Called on the UI thread, during Rdraw_frame / Rwait_frame. Set it after Rinit; NULL removes it.

Every widget reads its colors and sizes from a theme. A value is looked for in this order:

raven_text_editor.h

Multi-line text editor, and the languages it knows.

R_WIDGET_TEXT_EDITOR edits a text of any number of lines: selection with the mouse and the keyboard, clipboard, undo and redo, line numbers, word wrap. It scrolls by itself. In XML:

    <TextEditor Name="notes" Wrap="true" Placeholder="Write here"/>
    <TextEditor Language="Rust" LineNumbers="true" Slot.Fill="1"/>

Given a language, the editor colors the text, proposes words while typing (the words of the language and the names already written in the text), shows which bracket closes which, indents after an opening bracket, closes brackets and quotes, and comments lines out. C, C++, C#, Java, JavaScript, TypeScript, Python, Rust, GLSL, JSON, CSS, XML and HTML are built in; any of them can be changed, and others declared, with Rlanguage_register.

This is what the editor knows from the text alone. What needs to understand a whole program (the type of an expression, the errors of a compiler) comes from outside, through two doors: a completion callback that adds its own proposals, and markers that underline a part of the text with a message.

Positions are a line and a column, both starting at 0; a column is a byte offset in the UTF-8 text of its line. Out-of-range positions are clamped.

Keys: arrows, Home / End, Page Up / Down, with Ctrl to move by word or to the ends of the text and with Shift to select; Ctrl+A, C, X, V; Ctrl+Z, Ctrl+Y or Ctrl+Shift+Z; Tab and Shift+Tab indent the selected lines; Ctrl+Space proposes words; Ctrl+/ comments the selected lines out. A double click selects a word, a triple click a line.

raven_shell.h

What frames an application: its header bar and its docked panels.

HEADER BAR

A window created with R_WINDOW_CUSTOM_HEADER has no title bar from the OS: its content covers the whole window and draws the title bar itself. The simplest way is a R_WIDGET_HEADER_BAR at the top of the content:

    <Window Title="Notes" CustomHeader="true" Width="900" Height="600">
      <VBox>
        <HeaderBar>
          <Button Text="Open" Style="Flat"/>
          <TextInput Placeholder="Search" Width="180" Slot.HAlign="Right"/>
        </HeaderBar>
        ...
      </VBox>
    </Window>

The bar shows the title of the window and the close / minimize / maximize buttons, and holds any widget: its children are placed from the left, and from the right for those with Slot.HAlign="Right". Dragging the bar moves the window, a double click maximizes it, the edges of the window resize it: all of that is done by the window system itself where it can (Windows: snapping, the system menu and the shake gesture keep working).

Any other widget becomes a handle to move the window with Rwidget_set_window_drag (raven_widget.h), without a header bar at all.

DOCK AREA

A R_WIDGET_DOCK_AREA arranges its children as panels with a tab each: side by side, one above the other, or stacked behind the same tabs. The user drags a tab to move its panel elsewhere, drags the borders to resize, and closes panels. In XML, how a child is docked is given by its slot:

    <DockArea Name="dock" Slot.Fill="1">
      <TextEditor Name="source" Slot.Title="Source"/>
      <TreeView Name="files" Slot.Title="Files" Slot.Dock="Left" Slot.DockSize="0.22"/>
      <ListView Name="log" Slot.Title="Output" Slot.Dock="Bottom" Slot.DockSize="0.3"/>
      <Label Slot.Title="Problems" Slot.Dock="Tab" Slot.DockTo="log"/>

Node Graph

Nodes on a canvas that pans (drag the background, or the middle button) and zooms (the wheel). A node has a title, input pins on its left, output pins on its right, and may hold any widget (a slider, a color picker, a preview). The user links an output to an input by dragging from one pin to the other; dragging a link away from its input removes it. Links are wires: they hang between their pins, swing when a node is moved and settle, and carry a slow flow from their output to their input.

   <NodeGraph Name="graph">
       <Node Name="noise" Title="Noise" X="40" Y="60" Color="#FF9F0A">
           <Input Name="scale" Label="Scale" Type="number"/>
           <Output Name="value" Label="Value" Type="number"/>
           <Slider Value="0.4"/>
       </Node>
       <Node Name="blend" Title="Blend" X="320" Y="90">
           <Input Name="a" Label="A" Type="number"/>
           <Output Name="out" Label="Result" Type="number"/>
       </Node>
       <Link From="noise.value" To="blend.a"/>
   </NodeGraph>

Pins have a type, a free text ("number", "color", "mesh"...): an output only links to an input of the same type, or to a pin without a type. Each type has a color (Rnode_graph_set_type_color, or one Raven picks from its name); a link shades from the color of one pin to the color of the other. An input takes one link (a new one replaces it); an output feeds as many as wanted.

Nodes, pins and links are named by the integers the functions return, all different within one graph.

Block editor

Programs made of blocks that snap into each other, in the style of Scratch: a palette on the left (one block of each kind, by category), the scripts on a canvas that pans (drag the background, middle button) and zooms (Ctrl + wheel).

A kind has a label: words and slots. %n a number, %s a text, %b a condition, %r any value, %m a choice in a menu (its choices : Rblock_editor_set_slot_options); {text} right after a slot is its default; | separates the sections of a C block (each one is followed by a mouth): "repeat %n{10}", "if %b then|else", "%n + %n".

Blocks are named by integers (> 0). A block hangs under another one (R_BLOCK_NEXT), in a mouth of a C block (R_BLOCK_BODY, index = the mouth) or in a value slot (R_BLOCK_INPUT, index = the slot), or is the top of a script of its own.

The user drags a block with what is under it; the place it would go opens and shows its shadow; dropped on the palette, it is deleted. A left click selects a block (Ctrl / Shift : adds it), a left drag on the canvas draws a selection rectangle, and dragging a block of the selection moves the whole selection; Delete removes it. A right drag (or middle, or Alt + left) pans, a right click opens the context menu. A click on a script fires the clicked callback (to run it); the application makes the running blocks glow.

raven_viewport.h

Embedding content rendered by the application.

A VIEWPORT widget reserves an area of the layout and shows external content in it. Three modes cover every graphics API:

1. Texture (Rviewport_set_texture)

     The application renders to an image and Raven draws it like any widget:
     it is clipped, can have UI on top, and follows the layout exactly.
       - Vulkan : wrap your VkImageView with
                  Rvulkan_texture_create_from_image_view (raven_vulkan.h), zero copy.
       - OpenGL : share memory with Rvulkan_texture_create_shared and
                  GL_EXT_memory_object (zero copy), or read pixels back and
                  call Rtexture_update.
       - Any    : Rtexture_update with CPU pixels.

2. Draw callback (Rviewport_set_draw_callback)

     Raven calls the application while it records its own frame, with the
     viewport and scissor set to the widget. The application draws straight
     into the window: no intermediate image, UI can still be drawn on top.
     With the Vulkan backend the callback receives the VkCommandBuffer.
     The callback runs on the render thread.

3. Native child window (Rviewport_set_native)

     Raven creates a child OS window (HWND / X11 Window) kept on the widget.
     The application attaches its own swapchain or context to it: OpenGL,
     Vulkan, Direct3D, anything. Raven cannot draw over or clip that area.

Input: a viewport is focusable and forwards its mouse and keyboard events through Rwidget_set_event_callback.

raven_shader.h

@file raven_shader.h Effects: fragment shaders that color a rounded rectangle.

An effect is a fragment shader that Raven runs on a rectangle of a widget, with rounded corners, anti-aliased edges, the clipping and the opacity of the widget already taken care of. It receives where the pixel is (0..1 in the rectangle, and in pixels), the size of the rectangle, two colors, four parameters, the time, an optional texture and, when it asks for it, what was drawn behind the rectangle (sharp and blurred).

Raven comes with effects of its own (REffect: aurora, shimmer, neon edge, ripple, plasma, grain, spotlight, mesh gradient), and an application can write its own in GLSL, compiled to SPIR-V with glslangValidator or glslc:

    #version 450
    #extension GL_GOOGLE_include_directive : require
    #include "raven_effect.glsl"          // include/raven/shaders in a package
    vec4 raven_effect(RavenEffect fx) {
        float wave = 0.5 + 0.5 * sin(fx.uv.x * 12.0 + fx.time * 3.0);
        return mix(fx.color, fx.color2, wave);   // straight alpha
    }

Building windows and widget trees from XML.

<Window Title="Editor" Width="1280" Height="720">

      <VBox>
        <Label Text="Hello" Slot.Padding="8" Slot.HAlign="Center"/>
        <HBox Slot.Fill="1" Spacing="4">
          <Button Name="save" Text="Save" OnClicked="file.save"/>
          <Viewport Name="scene" Slot.Fill="1"/>

- An element is a widget; its tag is the widget type (VBox, Button, ...). - Child elements are child widgets, in order. - Attributes set properties. Attributes starting with "Slot." set the

    slot of the widget inside its parent (same meaning as Rslot_set_...).

- Tags and attribute names are not case sensitive. - Name="..." gives the widget a name for Rwidget_find. - OnClicked / OnChanged / OnCommitted / OnActivated="name" set the action

    of the widget (Raction_bind).

NEW TAGS

A document can declare its own tags: a <Widget> names a piece of interface, with parameters, and is then used like any built-in widget.

    <Widget Name="Field" Label="Name" Hint="" Wide="false">
      <HBox Spacing="8">
        <Label Text="{Label}:" Width="{Wide ? 140 : 90}"/>
        <TextInput Placeholder="{Hint}" Slot.Fill="1"/>
        <Children/>
      </HBox>
    </Widget>
    <Field Label="Email" Hint="you@example.com" Name="email"/>
    <Field Label="Password" Wide="true"><Button Text="Show"/></Field>

- The attributes of <Widget> other than Name are its parameters, with

    their default values.

- Inside it, {...} is computed: a parameter, or an expression of them

    (+ - * / %, comparisons, && || !, a ? b : c, 'text', min, max, round,
    floor, ceil, abs, len, upper, lower, empty, default). "{{" is a brace.

- <Children/> is replaced by the children given where the tag is used;

    <Children Name="x"/> by those marked Into="x".

- Where the tag is used, the attributes that are not parameters go to the

    widget it becomes (Name, Slot.Fill, OnClicked, Material...).

- If="..." keeps or drops an element; <Repeat Count="3" Var="i"> and

    <ForEach Items="a|b|c" Var="item"> repeat their content;
    <Include Source="file.xml"/> brings in another file.

- A declaration is known from the moment it is read until the library

    shuts down, in every document loaded afterwards.

Live reload

What is created from a file (Rwindow_create_from_xml_file, Rwidget_create_from_xml_file, the files they <Include>, the files of Rxml_register_widgets_from_file, the theme files) follows its file: save it in any editor and the window changes while the application runs. raven_locale.h

Translations and the conventions of a language.

Translations live in CSV tables: one row per text, one column per language. The first row names the columns: "key", then a language code per column (the codes are free: "en", "fr", "pt-BR", "ar"...).

    key,en,fr,ar
    menu.file,File,Fichier,ملف
    greeting,"Hello, {0}!","Bonjour, {0} !",مرحبا {0}
    files.one,{n} file,{n} fichier,ملف واحد
    files.other,{n} files,{n} fichiers,{n} ملفات

The usual CSV rules apply: fields with commas, quotes or line breaks are quoted, "" inside quotes is one quote. Lines starting with # are comments. A UTF-8 BOM is accepted. Several tables can be loaded: they add up, and a key loaded again replaces the old text. A table loaded from a file is read again when the file is saved, while live reload is on (Rxml_set_live_reload).

In C:

    Rlocale_load_csv("strings.csv");
    Rlocale_set_language(Rlocale_get_system_language());
    Rlabel_set_text(label, Rtr("menu.file"));

In XML, an attribute that starts with @ is a key: the widget shows its translation and follows the language when it changes ("@@" for a text that really starts with @):

    <Button Text="@menu.file" Tooltip="@menu.file.tip"/>

and a document can load its tables itself:

    <Strings Source="strings.csv"/>

A key with no translation in the language shows the text of the fallback language (the first column, or Rlocale_set_fallback_language), then the key.

The functions are for the UI thread. The strings they return stay valid until the tables or the language change (Rtr), or for the next 16 calls (Rtr_format, Rtr_plural, Rlocale_format_number).

Interfaces for everyone.

Screen readers. Every window of Raven is exposed to the screen reader of the system: UI Automation on Windows (Narrator, NVDA, JAWS), NSAccessibility on macOS (VoiceOver), AT-SPI on Linux (Orca). raven_backend.h

Rendering backend interface.

C only: not part of the bindings of other languages.

Include this header only to write a backend (OpenGL, Direct3D, Metal, or on top of another renderer such as HRL). Applications do not need it.

Raven turns the widget tree into a flat list of *instances*. Every primitive of the UI is one instance: a quad expanded by the vertex shader and shaded analytically (signed distance) by the fragment shader. A backend only has to 1. manage one presentation surface per window, 2. manage textures, 3. upload the instance array and issue one instanced draw per command, 4. optionally, keep a blurred copy of the frame for the glass primitives.

The reference shaders are src/render/vulkan/shaders/ui.vert and ui.frag.

Threading: every function of the table is called from a single thread, the render thread (or the UI thread when the render thread is disabled).

raven_web.h

Declared in raven_web.h, which is not included by Raven.h; part of the same library.

Raven Web raven_web.h : web pages inside a Raven interface.

A separate, optional library (target raven_web, CMake option RAVEN_BUILD_WEB). Raven itself knows nothing about it; it only uses the public functions of Raven, and an application that does not link it pays nothing.

It does not contain a browser. It drives one that is already installed: any browser of the Chromium family (Microsoft Edge, which comes with Windows 10 and 11, Google Chrome, Chromium, Brave...). The browser runs hidden, in its own process, with a profile of its own; Raven Web talks to it through a pipe (the DevTools protocol) and:

- receives the picture of the page each time it changes, and shows it

    in a texture, as any image of the interface: it can be clipped,
    scrolled, put under glass, animated;

- sends it the mouse, the keys and the text the widget receives; - runs JavaScript in the page and receives messages from it.

So HTML, CSS and JavaScript are those of a real, up to date browser, and the library weighs a few thousand lines. The price: a browser must be installed (Rweb_is_available tells), pages are pictures that arrive a frame late, and the cursor does not change over links.
