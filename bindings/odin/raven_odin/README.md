# Raven for Odin, the idiomatic layer

`raven_odin` is a hand-written layer over the generated binding in `../raven`
(which stays as it is and is used here as the raw package). It is optional:
programs that import `raven` keep working.

What it changes for the user:

- Odin `string` and `bool` instead of `cstring` and `i32`.
- Values written through pointers come back as results:
  `width, height := raven.window_get_size(window)`.
- Handles are separate types (`Window`, `Widget`, `Timer`): passing a window
  where a widget is expected does not compile.
- Enums are Odin enums (`.Left`, `.Label`) and flag groups are `bit_set`s.
- Callbacks are normal Odin procedures. No `proc "c"`, and the `context` of
  the code that registered the callback is restored when it runs.
- The errors of Raven go to `context.logger` (`core:log`) of the code that
  called `init`, or to a procedure given to `error_set_callback`.
- `raven.allocator()` is the heap of Raven as an Odin allocator.

```odin
package hello

import raven "ext:raven_odin"

main :: proc() {
	if !raven.init() {
		return
	}
	raven.window_create_from_xml(`<Window Title="Hi"><Button Text="Quit" OnClicked="quit"/></Window>`)
	raven.action_bind("quit", proc(sender: raven.Widget, action: string, data: rawptr) {
		raven.quit()
	})
	for raven.wait_frame() {}
	raven.shutdown()
}
```

Point a collection at the bindings folder and link the shared library as for
the raw binding (see `../README.md`):

    odin run . -collection:ext=<Raven>/bindings/odin -extra-linker-flags:"-L/path/to/lib -Wl,-rpath,/path/to/lib"

The package is named `raven_odin` because Odin refuses two packages of the
same name in one build; the import alias gives `raven.` in the code.

## What is here

| File | Content |
|---|---|
| `enums.odin` | Generated by `tools/bindgen` (`gen_odin_wrapper.py`): all C enums, with `bit_set`s for the flag groups. Checked by `bindgen.py --check`. |
| `handles.odin`, `core.odin` | Typed handles; `init`, `shutdown`, `quit`, `draw_frame`, `wait_frame`, `run`, `exit_code`. |
| `callbacks.odin` | Actions, timers and the frame callback with Odin procedures. |
| `errors.odin` | `error_get_last`, `error_set_callback`, and `error_log`, which writes to `context.logger`. The callback can run on the render thread of Raven. |
| `memory.odin` | `allocator`, `memory_check`, `memory_trim`. |
| `window.odin`, `widget.odin` | Windows from XML, size and title, `window_capture`, input injection, XML parsing with the position of a mistake, widget lookup, labels and text inputs. |
| `example/main.odin` | The example of `../example` through this layer. `-- --test` runs it without a window. |
| `functions.odin` | Generated by `tools/bindgen` (`odin_functions.py`): the functions of the C API that map by fixed rules, about 940 of the 1130. The rules are listed at the top of the file, and so are the functions that are not wrapped, with the reason. Checked by `bindgen.py --check`. |
| `callbacks_test.odin`, `frontdoor_test.odin`, `functions_test.odin` | `odin test`, headless. |

## What is generated, and what is not

`functions.odin` wraps a function when every parameter and the result are of a kind the rules know:
a handle of a known kind (`Widget`, `Window`, `Texture`, `Font`, `Tree_Item`...), a number, a boolean, an
enumeration, a text, or a number written through a pointer. The rules are in `tools/bindgen/odin_functions.py`.

- A function that returns a handle comes with `ok`, false for `R_INVALID_ID`: `item, ok := raven.tree_view_get_item(tree, 0)`.
- An `int` is a `bool` when its name says so (`widget_is_enabled`, a parameter `enabled`) or when the
  documentation of the result names `R_TRUE`. Any other `int` stays an `i32`.
- A text that the documentation says may be NULL is a `cstring`: `nil` is NULL, and a literal costs nothing.
  Other texts are `string`s. A returned text is a view into memory owned by Raven.
- A group of flags stays a `u32` for now.

A function the rules do not know stays **raw only**: call it through the raw package
(`import raw "ext:raven"`) in the same program. These are the functions that take a callback (they are the
next part), a `void*`, a buffer or a structure, and the handle parameters whose name the rules do not know.
A function that is added to the C API is raw only until the rules know it, and `bindings_up_to_date`
fails until `functions.odin` is generated again, so the change shows in review.

A procedure written by hand in another file of this folder replaces the generated one of the same name.
